## Concrete proposed policy

Opt in one reviewed source/tenant at a time. For an Activity with an explicit qualified numeric session ID, use versioned host + session identity independent of mutable title/schedule. Keep the database listing UUID and original dedupe key on adoption and subsequent `ON CONFLICT(dedupe_key)` imports. Distinct numeric series remain separate even when title and venue coincide; different event IDs in the same series remain occurrences, with dates/schedules retained by the collector. An Event, an ambiguous session, missing/malformed metadata or an unqualified source cannot claim this Activity policy.

Non-enrolled sources retain the current identity policy. Enrolled sources must provide validated metadata: do not silently fall back when an older collector omits it. Rollout therefore requires coordinated writer deployment, explicit session-derived dedupe keys, database enforcement and registry gating. The prototype refuses a dedupe key owned by a different identity. Concurrent uniqueness conflicts must be explicit failed/retryable saves, never successful freshness; multi-connection PostgreSQL concurrency verification is still required before release.

Changing session identity, source/tenant, place or retirement is a separate reviewed operation. A new numeric series is not automatically a rename of an old series. A move must wait for #40's canonical decisions; absence/failed fetch is not retirement, and withdrawn rows are not automatically revived. No merge/delete is proposed here. #135 retains historical content corrections. Existing reviewed field protections, review actors and audit history remain mandatory; this prototype is not a replacement for the operations review RPC.

Before a real forward action: freeze exact IDs, full row fingerprints, provider facts and actor-approved mappings; lock rows and identity namespace in one transaction; reject changed/missing rows, duplicate mappings and target collisions. Snapshot before/after facts and retain provenance/review history. An inverse is allowed only against the exact post-action fingerprint and after checking all inserted/dependent rows and uniqueness constraints; changes or new provider rows require a freshly reviewed inverse, never deletion or overwriting of later imports. The harness proves a clean inverse and refusal after later updates/additions, not a production concurrency guarantee.
